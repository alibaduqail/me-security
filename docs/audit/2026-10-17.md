# ME Security investigation and verification, 2026-10-17

What this repo does: ME Security attaches an owner-controlled permission policy to an AE2 grid through an ME Security Terminal cable part. Build controls physical AE2 hardware changes; View, Insert, Extract, and Craft control player network use. This audit assumes a normal multiplayer server with concurrent owners, trusted players, outsiders, and machine automation at Minecraft's normal tick rate. It does not establish a production load benchmark.

The audit fixed eight reproduced defects. The existing ordinary Drive mining and wrench protections already passed the baseline and were preserved. Existing uncommitted changes were retained; the initial source, documentation, tools, and configuration were archived before editing in `/tmp/me-security-audit-20261017/before.tgz`, with the original Git diff and status alongside it. No AGENTS.md was found in the checkout or its ancestor directories.

The build remains 1.1.0-dev.2, payload protocol 5. The checked build configuration and mod metadata pin Minecraft **1.21.1**, NeoForge **21.1.250**, Java **21**, AE2 **19.2.17**, GuideME **21.1.1**, and optional AE2 Wireless Terminals **19.5.1**. Executed Java runtime: Temurin 21.0.1, arm64; Gradle wrapper: 9.2.1. Dependencies and save formats were not upgraded.

The current README and guide define manual Build-authorized handling of physical storage cells, disallow external cell-slot automation on protected grids, preserve ordinary item/fluid automation and internal IO Port processing, and protect native network hardware from explosions. These existing network-wide rules were retained. No Secure Drive, PIN, owner-only ordinary Drive mining, or new automation policy was introduced.

## Investigation and executed checks

The audit traced physical break events, AE2 wrench dismantling, rotation, in-place upgrades, recoloring, multipart selection, memory cards, attunement, facades, menu construction/actions, storage transactions, crafting submission/collection, and optional wireless shortcut sources through their server-side mutations. AE2 and Wireless Terminals class files from the exact cached dependency JARs were inspected using decompilation and `javap`, including the nested Wireless Terminals API. These checks use the pinned implementation rather than assumptions about another AE2 release.

The addon policy packets derive the actor from the server context, require the active menu/container ID at dispatch, and revalidate ownership, live terminal identity, loaded position, distance, target entries, revision, and confirmation in the management menu. They carry a target UUID and edit intent, not a client-supplied actor or authority. AE2 menu packets are checked in the enqueued server-thread dispatch and mutation hooks. Unknown integrations are outside the advertised boundary.

Network `IActionSource` checks preserve player identity. Player-menu storage enforces its menu player's authority even if given a machine source. Actual machine sources without a player principal continue to transfer resources. Existing tests cover simulated and actual item/fluid transactions, direct ME Chest storage, cached cell handlers on all faces, public cells becoming protected, and ordinary chest input automation. The manual-only physical-cell rule is documented, rather than inferred from null-player storage actions.

Additional in-world tests now exercise ordinary Drives, Interfaces, Controllers, wireless access points, P2P parts, terminals, cable buses, and existing crafting/quantum/spatial fixtures. `nativeHardwareAndRevokedDriveActions` verifies mining, wrench removal, rotation, stale Drive menus, pickup, quick move, number-key swap, throwing, pickup-all, drag insertion, and direct quick-move/swap calls after revocation. It also permits Build-authorized Controller mining. Existing Drive coverage checks Build without Extract and conservation of a filled cell through authorized dismantling.

`terminalBlockEntityReloadPreservesOwnership` serializes the real cable bus, removes and recreates its block entity, waits for grid initialization, checks terminal identity/owner/trust/Drive protection, opens management as the owner, removes the terminal, and verifies a newly placed terminal gets a fresh identity and owner. Existing tests cover world-policy and CPU-claim serialization, missing-policy denial, conflict recovery, loaded splits/rejoins, unpowered protection, disconnected colors/parts, and retired identities. This block-entity reload is not a full real-client chunk-unload or reconnect test.

## Runtime checks still requiring manual execution

The automated two-identity checks use real server-side `ServerPlayer`/FakePlayer instances and AE2 mutation paths. No pair of connected graphical clients was driven in this audit. Human UI/packet timing, real reconnects, complete multi-chunk unload/reload order, and live quantum-bridge transport remain unverified. No current production-scale tick benchmark, third-party mover compatibility matrix, or dependency advisory scan was executed. Source inspection found that `SecurityGridService` scans grid nodes each tick, including collecting topology footprints; that remains a profiling target, not a measured performance defect.

Use a disposable world for the following checks. A server can be launched without using an existing development world with this temporary override:

```groovy
// /tmp/me-security-manual.gradle
afterProject { p ->
    if (p == p.rootProject) {
        p.neoForge.runs.multiplayerServer.gameDirectory =
                p.layout.projectDirectory.dir('run/audit-manual-server')
    }
}
```

Create `run/audit-manual-server/eula.txt` with the accepted EULA setting and `server.properties` with `server-ip=127.0.0.1`, `server-port=25565`, `online-mode=false`, `enforce-secure-profile=false`, `spawn-protection=0`, `gamemode=survival`, `view-distance=2`, and `simulation-distance=2`. Run these in separate terminals from the repository root:

```sh
./gradlew runMultiplayerServer -I /tmp/me-security-manual.gradle -x prepareLocalMultiplayerServer --offline --console=plain
./gradlew runOwnerClient -PserverAddress=127.0.0.1:25565 --offline --console=plain
./gradlew runGuestClient -PserverAddress=127.0.0.1:25565 --offline --console=plain
```

Repeat the matrix with `-PwithWireless=true` on all three commands. Use the same built candidate on both clients and server. Grant temporary creative mode from the console to assemble fixtures, then return Guest to survival for theft/conservation checks.

1. As Owner, build a powered grid with the Security Terminal, an ordinary Drive containing one cell with 12 diamonds, Controller, Interface, wired/crafting terminals, P2P tunnel, storage/conversion monitor, and a wireless access point. Add a working crafting CPU, Pattern Provider/Molecular Assembler, and a simple encoded recipe. Install a view cell in the wired terminal. Record cell and item counts.
2. With Guest untrusted, attempt mining, sneak-wrenching, rotation, memory-card loading/saving, recoloring, P2P attunement with a chest/cable, facade installation, and monitor configuration. Expect no hardware/configuration change and no consumed item. Ordinary Drive protection must behave the same as other hardware.
3. Trust Guest with View only. Opening the storage UI should work. Test network pickup, shift-click, hotbar swaps, dragging, double-click collection, and fluid containers; network movement must remain denied. Attempt to remove or insert terminal view cells; expect denial. Drive configuration/cell access remains denied.
4. Grant Insert, Extract, and Craft separately and repeat the matching positive operation. Test manual crafting ingredients with and without Extract. Request a completed multi-item craft with Craft alone, collect one item, then the remainder: every requested item must be collectible once and extra stock must remain unavailable. Repeat using the real wireless menu and fluids.
5. Grant Build alone. Guest should be able to manage/remove cells, configure hardware, attune P2P tunnels, install facades, edit monitor settings and view cells, and mine/wrench ordinary Drives and Controllers. Guest must still be unable to manage security or patterns or dismantle the Security Terminal. Verify the filled cell's contents after dismantling.
6. Leave Guest's Drive/configuration screen open. Revoke Build as Owner, then immediately try every inventory gesture, quick move, hotbar swap, drag, rotation, and configuration button. Expect closure/denial, intact cell contents, and no duplicate/lost carried item. Repeat trust removal with a storage and wireless menu open. Replace a host while its screen is open and test the stale screen.
7. Without Build, retain Insert/Extract and use a locked conversion monitor. Deposits and withdrawals should work. Sneak-clicking its lock and changing its displayed item should fail. Check denial feedback and inventory reconciliation on both clients.
8. Pair a Wireless Terminals crafting item, enable pick-block, use it nearby, move 128 blocks away, and immediately use pick-block again. Expect no replacement/deposit/withdrawal at range; return nearby and retry. Repeat restock, stow, pickup-to-ME, and permission revocation. For quantum access, install the supported quantum bridge/card/singularity configuration and verify its native valid/invalid link states still control access.
9. Run a hopper against Drive, chest, IO Port, and Spatial IO Port cell slots. Physical cells must stay put on protected grids, while normal chest input and import/export item/fluid automation continue. Process a manually inserted cell in an IO Port. Remove the terminal as Owner and verify public cell handling resumes.
10. Transfer ownership through the typed-name confirmation. Verify the new owner can manage/remove the terminal, the previous owner loses access unless separately trusted, and other trust entries persist. Stop the server cleanly, restart the same world, reconnect both clients, and repeat permission/cell-count checks.
11. Build a cable line across several chunks away from spawn, for example from x=1024 to x=1136 at y=80,z=1024, with terminal/power at the first end and a Drive at the other. Move both clients far away and wait until console `execute unless loaded 1024 80 1024 run say TERMINAL_UNLOADED` confirms unloading. Return Guest to the Drive end first while the terminal chunk remains unloaded. Protection must remain conservative; then load the terminal and verify ownership and permissions. Repeat across a server restart and a player dimension change.
12. With all relevant chunks loaded, cut the cable as Owner. The verified detached grid should become public; reconnect as Owner and verify protection returns. Attempt to connect two separately protected grids by cable, recoloring, P2P attunement, or a supported quantum path. Normal prohibited merges should be rejected; if a nonstandard path creates a conflict, each owner must retain management access and be able to wrench their own terminal to recover.
